#### `deep_researcher.py` 的节点和子图

- `clarify_with_user`：根据消息判断是否需要追问；需要时以 `END` 返回问题，否则写入确认消息并继续。
- `write_research_brief`：把对话转换成结构化 `research_brief`，初始化监督器消息。
- `supervisor`：使用 `ConductResearch`、`ResearchComplete`、`think_tool` 规划和调度研究。
- `supervisor_tools`：执行监督器工具调用；最多按 `max_concurrent_research_units` 并行运行研究员子图，并汇总原始笔记。
- `researcher`：加载搜索/MCP/思考工具，调用研究模型。
- `researcher_tools`：并行执行工具调用；达到 `max_react_tool_calls`、调用 `ResearchComplete` 或无工具调用时进入压缩。
- `compress_research`：将研究员消息压缩成带来源的结果，同时保留 raw notes。
- `final_report_generation`：将研究简报、用户消息和全部 notes 交给报告模型；遇到上下文超限时逐步截断重试。
- `execute_tool_safely`：工具调用的统一异步包装。

图关系为：

```text
START
  -> clarify_with_user
      ├─ 需要澄清 -> END（返回问题，等待下一次输入）
      └─ 不需要 -> write_research_brief
                    -> research_supervisor
                       -> supervisor <-> supervisor_tools
                          ├─ ConductResearch
                          │   └─ 并行 researcher_subgraph
                          │       -> researcher <-> researcher_tools
                          │          -> compress_research -> END
                          └─ ResearchComplete/无工具/超限 -> END
                    -> final_report_generation -> END
```

### 3.3 部署认证：`src/security/auth.py`

通过 LangGraph `Auth` 注册认证中间件。`get_current_user` 解析 Bearer JWT 并调用 Supabase 校验；线程、assistant 和 store 的钩子写入 owner 或返回 owner 过滤条件，从而限制用户只能访问自己的资源。`langgraph.json` 的 `auth.path` 指向该模块的 `auth` 对象。Studio 用户会被视为内部用户而跳过 owner 过滤。

## 4. 系统完整工作流程

### 4.1 启动和配置加载

1. LangGraph 根据 `langgraph.json` 导入 `deep_researcher`。
2. 每个节点通过 `Configuration.from_runnable_config` 读取配置；优先使用同名大写环境变量，否则使用 `configurable`，未提供则使用 Pydantic 默认值。
3. 模型通过 `init_chat_model` 延迟初始化。默认角色是：摘要 `openai:gpt-4.1-mini`，研究/压缩/报告 `openai:gpt-4.1`。
4. API key 默认从环境变量读取；当 `GET_API_KEYS_FROM_CONFIG=true` 时改从运行配置的 `apiKeys` 读取。

### 4.2 澄清和研究简报

1. 输入状态只有 `messages`。
2. `clarify_with_user` 使用结构化 `ClarifyWithUser` 判断问题是否足够明确。
3. 需要澄清时立即返回问题，外部客户端补充消息后重新运行；不需要时继续。
4. `write_research_brief` 使用 `ResearchQuestion` 生成单一、具体、包含用户约束的研究简报，并初始化监督器系统提示和用户任务。

### 4.3 监督器调度

1. `supervisor` 绑定三个工具：思考、研究委派、完成信号。
2. 模型先用 `think_tool` 规划，再调用一个或多个 `ConductResearch`；提示明确要求每次委派后再次思考。
3. `supervisor_tools` 同批处理思考结果，并将研究任务限制在最大并发数内。
4. 每个委派任务创建独立 researcher state，异步并行运行。
5. 研究结果以 `ToolMessage` 回填监督器；raw notes 聚合到主状态。
6. 达到迭代上限、没有工具调用、收到 `ResearchComplete` 或异常时结束监督器子图。

### 4.4 研究员工具循环

1. `get_all_tools` 组合 `ResearchComplete`、`think_tool`、选定搜索工具和可选 MCP 工具。
2. 搜索 API 选择：
   - `TAVILY`：自定义 `tavily_search`；
   - `OPENAI`：原生 `web_search_preview`；
   - `ANTHROPIC`：原生 `web_search`；
   - `NONE`：不添加搜索工具，仍可使用 MCP（若配置）。
3. 研究模型读取 `research_system_prompt`，可以连续生成搜索、思考和 MCP 工具调用。
4. 工具调用通过 `asyncio.gather` 并行执行，结果写成 `ToolMessage`。
5. 无工具调用、收到完成信号或达到 `max_react_tool_calls` 后转入压缩；否则把工具结果追加回模型继续循环。
6. Tavily 会并行执行多个查询、按 URL 去重、截断网页内容，并使用摘要模型结构化生成摘要。
7. MCP 若要求认证，则通过 Supabase token 换取 MCP token，存入 LangGraph store，并在工具报错时转换为用户可理解的交互提示。

### 4.5 压缩、汇总和最终报告

1. `compress_research` 将研究员的 AI/工具消息交给压缩模型，保留查询、事实和来源引用，输出 `compressed_research` 与 `raw_notes`。
2. 监督器把压缩结果作为自己的工具观察值，并在下一轮决定继续补充还是完成。
3. 监督器结束后，主图边自动进入 `final_report_generation`。
4. 最终报告模型收到研究简报、原始用户对话和汇总 notes，按用户语言输出 Markdown、标题、引用和 Sources。
5. 若上下文超限，按模型 token 上限估算字符截断，随后每次再缩减 10% 重试；非 token 错误直接返回错误状态。
6. 成功输出写入 `final_report` 并追加最终 AI 消息，同时清空主状态中的 `notes`。

## 5. 关键状态和调用关系

```text
AgentInputState(messages)
        |
        v
AgentState
  messages
  supervisor_messages
  research_brief
  raw_notes
  notes
  final_report
        |
        +--> SupervisorState
        |      supervisor_messages
        |      research_brief
        |      research_iterations
        |      raw_notes / notes
        |
        +--> ResearcherState（每个 ConductResearch 一份）
               researcher_messages
               research_topic
               tool_call_iterations
               raw_notes
               |
               +--> ResearcherOutputState
                    compressed_research
                    raw_notes
```

消息列表通常通过 `operator.add` 追加；监督器消息和 notes 支持 `{"type": "override", "value": ...}` 覆盖。这样既能保留多轮上下文，也能在开始新阶段时替换消息或清理 notes。

## 7. 当前实现与遗留实现的边界

当前入口采用“澄清 -> 简报 -> 监督器 -> 并行研究员 -> 压缩 -> 最终报告”的轻量多代理架构；遗留 `graph.py` 更偏“人工反馈的计划-执行”，遗留 `multi_agent.py` 更偏“章节级监督器/研究员”。不要把遗留配置字段、搜索 API 范围或测试入口误认为当前主图必然支持的行为。

## 8. 对“生产入口”表述的更正，以及原始路径说明

上一版把 `src/open_deep_research/deep_researcher.py:deep_researcher` 称为“生产入口”，表述不够严谨。准确说法是：

1. `langgraph.json` 明确配置的 **LangGraph 图入口** 是 `./src/open_deep_research/deep_researcher.py:deep_researcher`。因此，在 LangGraph Studio、LangGraph Platform 或 `langgraph dev` 场景下，它是研究图的运行入口。
2. 原始路径 `G:\Code\open_deep_research` 目前还包含一套后续扩展的自建 FastAPI + React + PostgreSQL 代码。若启动自建 Web 应用，应用入口是 `src/server/app.py:app`，典型命令写在 `src/server/__init__.py` 的说明中：`uv run uvicorn server.app:app --app-dir src --port 8000`。
3. 自建 FastAPI 入口并不替代研究图：`src/server/graphs.py` 导入 `deep_researcher_builder`，给它配置 PostgreSQL checkpointer 后重新编译。因此关系是“Web/API 入口 -> 持久化图管理器 -> 核心研究图”，而不是二选一。
4. `src/open_deep_research/` 是核心领域逻辑/计算层，不等于整个项目的 HTTP 生产入口。是否称为“生产入口”取决于部署模式；称为“核心 LangGraph 图入口”更准确。

### 8.2 核心图层与自建服务层的调用关系

```text
浏览器 web/src/
   │ HTTP + SSE
   ▼
src/server/app.py:app
   ├─ routers/sessions.py
   │    ├─ 创建/查询 ResearchReport
   │    ├─ 调用 graphs.manager.get_graph()
   │    └─ 流式转发 LangGraph 节点、消息、完成状态和 token 用量
   ├─ routers/documents.py
   │    └─ PDF/TXT/MD -> docstore.py -> 本地 JSON 向量索引
   ├─ routers/export.py
   │    └─ charts.py / exporters.py -> PNG、DOCX、PPTX
   └─ routers/health.py
        └─ 返回数据库、图和认证就绪状态
             │
             ▼
      src/server/graphs.py:GraphManager
        ├─ src/server/db.py -> Async SQLAlchemy/asyncpg
        ├─ AsyncPostgresSaver -> LangGraph checkpoint 表
        └─ deep_researcher_builder.compile(checkpointer=...)
             │
             ▼
      src/open_deep_research/deep_researcher.py
        └─ clarify -> brief -> supervisor -> researcher -> compression -> report
```

这里存在两类数据存储，不能混为一谈：

- `src/server/models.py` 定义业务表 `research_reports` 和 `usage_events`，用于会话归档、状态展示和用量统计。
- `AsyncPostgresSaver` 管理 LangGraph 的 checkpoint 表，用于保存消息、research brief、notes 和图运行状态；`ResearchReport.id` 同时作为 `thread_id`，把业务会话和图状态关联起来。
- `src/open_deep_research/docstore.py` 是独立的本地文档 RAG 索引，默认写入 `data/docs/docs_index.json`，不属于 PostgreSQL checkpoint。

### 8.3 原始路径各目录的职责

| 目录 | 角色 | 与其他目录的关系 |
|---|---|---|
| `src/open_deep_research/` | 核心研究引擎 | 被 `langgraph.json` 直接暴露，也被 `src/server/graphs.py` 导入并重新编译 |
| `src/server/` | 自建后端适配层 | 提供会话、SSE、文档、导出和健康接口；不复制研究算法 |
| `src/server/routers/` | FastAPI 路由 | `app.py` 注册；sessions 是主运行通道，documents/export 是外围能力 |
