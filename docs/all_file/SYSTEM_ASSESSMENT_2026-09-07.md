## 0. 总体结论

**一句话**：这是一个**研究内核一流、工程外壳早期**的系统——算法架构与上下文成本控制处于同类开源项目第一梯队，但把它包成可对外服务的产品层，尚未跨过"可运维、可观测、可信"的门槛。

**核心矛盾**：过去 9~10 人日的扩展把"能力清单"补齐了（RAG、代码沙箱、图表、导出、用量计量），但**能力的可达性与正确性未被验证**——3 个新检索引擎有 2 个因参数丢失 100% 失效（P0-1），迁移体系整体失效（P0-2），6 个后端端点前端零入口（P1-8）。即：**清单上打勾 ≠ 系统里可用**。

## 1. 架构设计评估（8.5 / 10）

### 1.1 值得肯定的设计

**① 双层多智能体 + 压缩回传 —— 这是全系统最重要的资产。**

```
主管 supervisor ⇄ supervisor_tools ──asyncio.gather──▶ N 个 researcher 子图
                                                        └─ compress_research
                        ◀── compressed_research（压缩摘要）──┘
```

关键在 `ResearcherOutputState`（`state.py:92-96`）**只暴露 `compressed_research` 与 `raw_notes` 两个字段**：研究员的原始网页/工具输出**永不进入主管上下文**。这使主管上下文成本随研究轮次**近恒定**，而非竞品"递归展开"式的线性膨胀。这是架构级、而非参数级的优势，难以被简单抄走。

**② 收窄的层间通道 + `override_reducer`**（`state.py:55-60`）：既解决"简报重置"又支持"notes 清空"，比常见全量覆盖方案干净。

**③ 扩展遵循"外围新增、内核少动"**：全案内核改动仅 3 处（`configuration.py` 增量字段、`utils.get_all_tools` 一次 `tools.extend`、`deep_researcher.py` 一行异常语义），`langgraph.json` 与核心图零改动。这是**正确的演进策略**，也是本次扩展能快速落地的原因。

### 1.2 架构层面的问题

| 问题 | 位置 | 影响 |
|---|---|---|
| **提示词承载控制流** | `prompts.py:12`（防澄清死循环）、`:103-110`（迭代软约束）、`:164-174`（"最多 5 次搜索"） | 改提示词即改行为，属隐性耦合；且 `:166-168` 硬编码的"5 次"与 `max_react_tool_calls=10` **不一致** |
| **`utils.py` 上帝模块** | 935 行混装搜索/MCP/OAuth/token 判定（占核心包 34%） | 扩展点与业务逻辑耦合，阻碍插件化 |
| **退出判定先于工具执行** | `deep_researcher.py:247-262` 早于 `264+` | 主管最后一轮发出的 `ConductResearch` **被静默丢弃**；默认 6 轮实际只有 6 轮生效，第 7 次进入即退出 |
| **计数与判定分离** | 计数在 `supervisor:221` / `researcher:423`，判定在 `supervisor_tools:247` / `researcher_tools:493` | 循环不变量需推导而非直读，易错 |
| **`supervisor_tools` 上帝函数** | `deep_researcher.py:225-350`，**126 行** | 退出判定 + think_tool + 并发派发 + overflow + raw_notes 聚合 + 异常兜底六职责 |
| **配置优先级反直觉** | `configuration.py:256` `os.environ.get(KEY, configurable.get(key))` | **环境变量恒覆盖每次运行的 configurable**；而 `retrievers.py:204-209` 反之——同仓库两套相反约定 |
| **`configurable_model` 模块级单例** | `deep_researcher.py:56-58` | 切换成本为零，但测试需 patch 模块属性 |

## 2. 研究能力评估（8.0 / 10）

### 2.1 硬成绩

Deep Research Bench RACE：**0.4309（默认）→ 0.4943（GPT-5）**，2025-08 时点榜单 #6。这是 100 道博士级任务、LLM-as-judge 的第三方榜单，含金量足够。

### 2.2 能力结构

| 能力 | 状态 | 说明 |
|---|---|---|
| 澄清式交互 | ✅ 内建于图 | `clarify_with_user:60-115` 三分支；澄清续聊复用同一 thread_id，检查点恢复上下文 |
| 并行研究 | ✅ | `asyncio.gather`（`deep_researcher.py:305`），默认 5 路并发 |
| 多模型分档 | ✅ | 摘要/研究/压缩/报告四种角色独立配置 |
| 多搜索源 | ⚠️ | Tavily + OpenAI/Anthropic 原生 + MCP；新增三引擎中 **2 个失效**（P0-1） |
| 本地文档 RAG | ⚠️ | 已实现但**前端无入口**（P1-8） |
| 代码沙箱 / 数据产物 | ⚠️ | 已实现，图表注入有脏读缺陷（P1-3），前端无入口 |
| 报告导出 | ⚠️ | PPTX/DOCX 已实现，前端无入口 |
| **引用校验** | ❌ | **纯提示词，无任何 URL 解析/去重/校验**（`prompts.py:212-219`、`:298-307`）。且压缩阶段 `[1] Title: URL` 与报告阶段 `[Title](URL)` 两套编号体系无对齐机制 |
| **持久记忆** | ❌ | 无 Store，跨会话零记忆；同时导致 MCP OAuth 不可用 |
| **质量自检 / 反思节点** | ❌ | 无"报告质量校验—重写"闭环，质量只靠提示词 |
| **用量配额** | ❌ | 有计量（`usage_events`）但无配额、无 429 拦截 |

### 2.3 最需要补的研究能力

1. **引用校验节点**（成本最低、收益最高）：在 `final_report_generation` 后加一个节点，用正则抽取报告中的 URL 与 `notes` 中的 URL 做集合比对，标记"引用了但来源里没有"的链接。**这是与 STORM/GPT-Researcher 的主要差距**，且不影响主流程。
2. **持久记忆层**：挂 Postgres Store（user 命名空间），同时解锁 MCP OAuth —— 一个改动解决路线图两项。
3. **报告质量自检**：用 `summarization_model` 做一次 groundedness 打分（评估脚本里已有类似逻辑 `tests/evaluators.py:136`），低于阈值触发重写。

## 5. 性能与成本（5.0 / 10）

### 5.1 架构级优势（真实且重要）

压缩回传 + 并行研究员，使上下文成本近恒定、墙钟时间显著优于串行方案。这是设计红利，不是调参红利。

### 5.2 运行侧的主要问题

| 问题 | 位置 | 影响 |
|---|---|---|
| **默认参数激进** | `max_concurrent_research_units=5` × `max_researcher_iterations=6` × `max_react_tool_calls=10` | 乘法关系；文档自估降档可省 40–60%（`TECHNICAL_SUMMARY.md:148-149`） |
| **摘要超时返回原文** | `utils.py:209`/`:213` | **比成功路径更贵**：原文已截到 50000 字符（≈12.5k tokens），且白付 60 秒请求。认证失败等异常同样塞全文 |
| **MCP 每轮重连** | `utils.py:500-501` new client；`get_all_tools` 每节点调用一次 | 每 ReAct 迭代 2 次握手 → 单次研究**最多约 100 次重连** |
| **并发无 semaphore** | `deep_researcher.py:291` 仅切片 | 无法跨轮次限流；超额任务返回错误 ToolMessage 而非静默丢弃（这点是对的） |
| **无缓存** | — | 相同查询/相同问题无复用 |
| **有计量无配额** | `usage_events` 已落地 | 计量数据前端还被丢弃（P1-8），无法驱动成本控制 |

### 5.3 建议（按性价比）

1. **先修计量可见性**（P1-8），让 `done` 事件的 `usage` 到达前端——否则无法验证任何调参效果；
2. 默认参数降档至 3×4×5，用 `tests/run_evaluate.py` 小样本验证质量不回退；
3. 摘要回退改为"截断到 8000 字符 + 保留小标题"，而非返回全文；
4. MCP client 按 `url+token` 缓存。

## 6. 可靠性与容错（4.0 / 10）

**系统性问题是"静默降级"过多**——几乎每处异常都选择继续而非上报，导致故障不可见：

| 静默降级点 | 位置 | 后果 |
|---|---|---|
| 检索工具异常 → 返回 "Error searching..." | `retrievers.py:83-84`、`:134-135` | 模型以为"没搜到"，P0-1 因此完全隐身 |
| 摘要超时/异常 → 返回原文 | `utils.py:209`/`:213` | 成本飙升且无告警 |
| MCP 配置不全 → `return []` | `utils.py:471-479` | 工具凭空消失，无 error 日志 |
| `compress_research` 异常 → 无差别 `continue` | `deep_researcher.py:574-575` | 不区分错误类型、不退避，3 次后返回失败串 |
| Gemini `ResourceExhausted`（含 429 限流）→ 判为上下文超限 | `utils.py:788-789` | **限流被当成超长，静默提前结束研究** |
| 健康检查恒 200 | `health.py:13` | 实例不可用仍接流量（P1-2） |
| 静态托管静默失败 | `app.py:43` 无 else | 前端不托管且无告警 |
| SSE 无断开检测 | `sessions.py:289-367` | 客户端断开后研究继续烧钱（P1-6） |

**其他可靠性问题**：

- `get_model_token_limit` 子串匹配（`utils.py:852`）：Gemini 2.x、gpt-5、claude-haiku-4-5 等新模型**返回 `None`** → `deep_researcher.py:669-675` 直接产出失败报告且**不重试**；`cohere:command`（4096）是 `command-r`（128000）前缀，顺序一变即低估 32 倍。
- `compress_research` 判限用错模型名：`deep_researcher.py:570` 传 `research_model`，实际调用的是 `compression_model`（默认同为 gpt-4.1，掩盖了 bug）。
- `compress_research` 对 state 列表原地 `.append()`（`deep_researcher.py:539`），与检查点快照假设相悖。
- **`or True` 移除后（P1-5）**：语义正确，但把"静默降级"换成"整次运行失败"，缺少中间策略（建议引入"失败子任务数阈值"）。

## 7. 安全性（5.0 / 10）

### 7.1 做对的（有明确威胁模型）

- **模型生成代码永不进主进程**：`sandbox.py` AST 白名单 + `python -I` 子进程 + 超时 + cwd 隔离；"安全红线"写在注释里。
- **报告 Markdown 渲染消毒**：`ReportView.tsx:7-19` 用 `rehype-sanitize`，注释明确记录了"网页抓取内容即 XSS 向量"的威胁模型。全仓无 `dangerouslySetInnerHTML`。
- **免鉴权模式带成本护栏**：`AUTH_MODE=local` 时钳制并发 1 / 迭代 2（`deps.py:64-78`）。
- **会话属主校验**：`_get_session()` 校验 `row.user_id`。

### 7.2 风险项

| 风险 | 位置 | 级别 |
|---|---|---|
| **默认免鉴权** | `deps.py:40-45`：无 `SUPABASE_URL` 即回落 `local`；`.env.example:26` 的 `AUTH_MODE=` 为空即触发 | **高** |
| 沙箱可被 `__import__` / `open()` 绕过 | `sandbox.py:35-44` 只拦 `import` 语句 | 中（子进程隔离兜底，但可写文件/出网） |
| 导出图片路径穿越 | `exporters.py:41` `os.path.join(base_dir, ref)` 未做归一化与前缀校验 | 中 |
| 无 DB 层租户隔离 | 检查点表无 user 列，隔离只在 API 层 | 中（多租户强合规需分库/RLS） |
| 弱凭据硬编码 | `docker-compose.dev.yml:8-10` `postgres/odr`，5432 直曝宿主 | 中（开发用，但易被复制到生产） |
| 无 CORS / 无全局异常处理 / 无限流 | `app.py` 全文 | 中 |
| MPLCONFIGDIR 临时目录泄漏 | `sandbox.py:80` 每次 `mkdtemp` 从不清理 | 低 |
| `src/security/auth.py` 的 `StudioUser` 豁免 | `TECHNICAL_SUMMARY.md:177` | 低（仅 LangGraph 平台接口） |

## 15. 关键结论三句话

1. **内核值得保留，外壳需要重做**：压缩回传的上下文架构与 BYO 配置化是真正的护城河，不要在重写中丢掉；需要重做的是外围的验证、观测与运维体系。
2. **当前最大的风险不是"功能不够"，而是"以为功能够"**：33 个单测全绿、清单五项打勾，实际 2/3 新检索引擎不可用、迁移体系整体失效。建立"能证明可用"的验证闭环（真实 invoke + 端到端 + CI）优先级高于新增任何功能。
3. **先计量、再调参、后扩展**：`usage_events` 已落地但数据到不了前端。让用量先可见，是后续所有成本优化与产品化动作的前置条件。
